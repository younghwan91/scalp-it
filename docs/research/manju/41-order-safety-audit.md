## 치명적 (돈을 직접 날리는 경로) — 첫 실발주 전 반드시 차단

### C-1. dry-run→live 오발동: 기존 `--dry-run` 에 주문을 엮으면 정상 실행이 곧 실발주
**가장 위험한 설계 함정.** CLI 의 `--dry-run` 은 기본값 **False** 이고, 그 의미는
"로그·웹훅·저장 안 씀(미리보기)"일 뿐이다. `run_live` 는 문서상 "실전 주경로"라 **평소
`--dry-run` 없이** 돈다(store=True, 실 WS 엔드포인트). 그러므로 주문 실행 조건을
`if not args.dry_run:` 같은 기존 플래그에 걸면 **매 정상 라이브 실행이 실주문을 낸다.**
- 요건: 주문 실행은 **기존 `--dry-run` 과 완전히 독립된** 별도 이중 게이트여야 한다 —
  `--live-order`(주문 활성) + `--confirm-real`(실계좌 재확인) **둘 다** 있을 때만.
  기본은 둘 다 꺼짐 → 주문 안 나감(로그에 "would place" 만).
- `--mock` 과의 관계도 못박아야: `--live-order` 인데 `--mock`(모의 WS)이면 주문 엔드포인트도
  반드시 모의(mockapi)여야 한다. WS 는 모의인데 주문은 실계좌로 가는 엇갈림 금지.
- 환경변수(예 `PAIR_LIVE_ORDER=1`)로 게이트를 열 수 있게 만들지 말 것 — 셸 export 잔존으로
  다음 실행이 무단 실발주된다. 게이트는 **명시적 CLI 플래그만**.

  가격·수량 필드가 뒤바뀌면 수천주가 될 수 있다. 수량은 상수 `1` 로 고정, 외부 입력에서
  절대 유도하지 말 것. `--qty` 같은 플래그를 두더라도 상한(assert qty==1 또는 ≤ 소량)을 코드로.
- **같은 신호 중복 발주**: 한 follower 가 여러 대장의 쌍에 속하면(`_by_leader` 는 leader 별
  목록, dedup 키는 `(leader, follower)`) 한 틱 배치에서 **같은 종목에 2건 이상 알림→2주**가
  나갈 수 있다. 요건: 주문 계층에서 **follower(종목) 단위 in-flight/보유 dedup** 추가.
- **재시도 루프 중복**: HTTP 5xx/타임아웃 재시도가 이미 접수된 주문을 재전송하면 2배 발주.
  요건: 주문은 멱등키/주문번호 확인 없이 자동 재시도 **금지**(조회로 확인 후에만).
- 가드 `max_positions=2` 는 **가상** 포지션 수 기준이라 실주문 수량 상한이 아니다.
  실주문 총 노출(종목수·주수·금액) 상한을 주문 계층에 별도로 둘 것.

### C-4. 가격 폭탄 — 지정가 이상치·방향 오류·무보유 매도
- 진입가 = `alert.entry` = `self._bid.get(fol, cur)`. **bid1 이 없으면 현재가(cur)로 폴백**한다.
  호가 갱신이 늦거나 0/None 이면 entry 가 비정상(0·직전 stale·상한가)일 수 있다.
  요건: 주문 직전 sanity — entry>0, 현재가 대비 ±X%(예 3%) 이내, 호가단위 정합(틱사이즈 반올림),
  상/하한가 밖이면 거부. 0원·비정상가 지정가 금지.
- **매수 전용**을 코드로 못박을 것. 이 전략은 bid1 지정가 **매수**만 한다. 매도 경로를 아예
  만들지 말거나(청산은 사람이), 만들면 "그 종목 매수 체결분 존재" 확인 없이는 매도 금지
  (공매도/무보유 매도 사고 방지). 방향 파라미터를 외부에서 받지 말 것.

### C-5. 킬스위치·손실한도가 **실주문 경로를 실제로 막지 않는다**
현 킬스위치는 "신규 **알림** 억제"만 한다(risk_guard 문서 명시). 그리고 손익은 **가상**
체결 기준. 주문을 붙이면:
- 손실한도(5만원)가 **실체결 손익**을 반영하지 못하면 한도가 무의미하다. 요건: 주문 계층은
  실체결(주문 응답/체결 조회) 손익으로 별도 카운트하거나, 최소한 **주문 실행 자체가
  `decision.allowed and not guard.killed` 를 반드시 통과**하도록 게이트. `_emit_guarded` 의
  통과 여부와 주문 발주를 **동일 게이트**로 묶을 것(알림은 났는데 주문은 별경로로 나가는 구멍 금지).
- 킬 발동 후 **미체결 지정가 주문 방치**: 킬은 신규만 막고 기존 미체결을 취소하지 않는다.
  요건: 킬 시 열린 실주문 전량 취소 로직(또는 최소한 사람에게 "미체결 N건 취소 필요" 경고).

## 중대 (조건부로 돈을 날리거나 통제 상실)

### M-1. 미체결·취소 실패 시 방치 포지션
90초 시간청산은 **가상** 로직이다. 실주문은 지정가 미체결이면 큐에 남는다. 청산 주문
실패·취소 실패 시 무한 보유. 요건: 미체결 주문 TTL·강제취소, 취소 실패 시 재확인·경보.
실계좌 청산을 자동화할 거면(안 하는 게 원칙) 청산 실패 경로를 반드시 설계.

### M-2. 계좌번호·시크릿 노출 위험(주문 도입 시 신규)
주문 API 는 계좌번호(CANO 등)를 새로 요구한다. 요건: 계좌번호를 로그·에러메시지·Discord·
포지션로그·커밋에 **절대** 남기지 말 것. env 에서만 읽고, 실패 메시지에 payload 통째로 찍지 말 것.
현재 토큰은 미노출이나, 주문 실패 디버깅 중 `print(response.json())`·`print(body)` 로
계좌번호·토큰이 새기 쉽다 — 주문 모듈의 모든 print/log 를 감사할 것.

### M-3. 동시성·장 상태
- **App key 1세션 제약**(문서 명시): 같은 키로 tick-collect 데몬과 --live 동시 실행 시
  thrash(105110). 주문 REST 는 WS 와 별세션이라 덜하지만, 토큰 공유·레이트리밋 충돌 가능.
- 여러 신호 동시 발주 → C-3 중복·C-5 한도 경합. 주문 계층은 **직렬화**(락/큐)로 한 번에 하나씩,
  각 주문 전 킬·한도·보유수 재확인.
- **장 시작/마감 동시호가·장외**: 지정가가 동시호가 구간에 들어가면 예상외 체결가.
  장 운영시간(09:00~15:20, 동시호가 제외) 밖 주문 거부 가드 권장.

### M-4. 테스트가 실주문 POST 를 실호출할 위험
요건: 주문 테스트는 반드시 httpx mock/transport 로. 실 base_url(https://api.kiwoom.com)로
가는 POST 가 단위테스트에서 절대 발생하지 않게. 테스트 기본 base_url=mock, `--confirm-real`
없이는 실 POST 함수가 호출되지 않는 구조. CI·로컬에서 실 env 키가 있으면 자동 스킵/모의화.

## 첫 실발주 전 필수 수정 TOP (order-module 에 전달)

1. **주문 게이트를 기존 `--dry-run` 과 분리** — `--live-order --confirm-real` 이중, 기본 꺼짐, env 우회 불가 (C-1).
2. **보유종목 차단 이중화** — (a) 하드코딩 000010·000020·222222 + (b) 주문 직전 kt00018 실시간 잔고조회로 전 보유종목 매수차단, 잔고조회 실패 시 fail-closed (C-2).
3. **수량 상수 1 고정 + 종목단위 중복발주 dedup + 무재시도** (C-3).
4. **진입가 sanity(>0, ±X%, 틱사이즈, 상하한가) + 매수전용·무보유매도 금지** (C-4).
5. **주문 발주를 가드 게이트(killed·allowed)와 동일 경로로 묶고, 킬 시 미체결 취소/경고** (C-5).
6. **계좌번호·토큰 로깅 금지, 테스트는 mock only** (M-2·M-4).

> 결론: 지금은 주문 코드가 없어 **당장의 실발주 사고 경로는 0**이다. 위험은 전적으로
> "주문을 어떻게 붙이느냐"에 달려 있고, 위 6개를 설계 시점에 박지 않으면 C-1(정상 실행이
> 곧 실발주)·C-2(보유종목 차단 부재)·C-3(수량 폭주)가 가장 현실적인 돈 날림 경로다.
