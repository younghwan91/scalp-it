## 0. 왜 재나

[72번](72-pair-live-rules-preregistration.md)은 지금 라이브 규칙을 **분봉**으로 근사해
기각했다(net64 4/4 폴드 음수). 그 문서가 스스로 밝힌 공백은 "분봉으로는 호가 두께·
체결강도·테마를 재현 못 한다"였다. 그 뒤 `ticks` 15.5M행·`quotes` 8.2M행이
2026-08-24~09-14 16거래일치 쌓였다. 이번엔 **저장된 틱·호가를 실제 `PairDetector`·
`RiskGuard` 에 그대로 흘려** 신호를 만든다 — 72번의 세 근사 한계(등락률 대리 서열·
1분 지연 청산·섹터 대체 테마)가 전부 실제 코드 경로로 바뀐다.

동기는 두 가지다. (1) 오늘(09-14) 감지기 후보 신호가 **3건**, 전부 필터 배제였다 —
"왜 이렇게 적나"에 데이터로 답해야 한다. (2) 필터는 1,000만원 주문을 가정하는데
실주문은 1주다. 필터를 풀면 나아지는지, 아니면 72번처럼 비용 앞에서 무너지는지를
**IS 에서만 고르고 OOS 에서 한 번만** 확인한다.

## 1. 표본 — 측정 전 고정

```
전체     틱이 있는 모든 거래일 2026-08-24 ~ 2026-09-14 (16일)
IS       첫 8거래일: 08-24, 08-25, 08-26, 08-27, 08-28, 08-31, 09-01, 09-02
OOS      뒤 8거래일: 09-03, 09-04, 09-07, 09-08, 09-09, 09-10, 09-11, 09-14
```

- 선택은 **IS 에서만** 한다. OOS 는 선택된 config **하나**와 라이브 config(기준선)에
  대해 **한 번만** 계산한다. 다른 셀의 OOS 표는 만들지 않는다.
- 구독 커버리지가 날마다 다르다(08-25 8종목·08-28 틱 6만행, 09-14 248종목). 날짜를
  빼거나 가중하지 않는다 — 있는 그대로가 "그날 우리가 볼 수 있었던 것"이다.
- 08-24~08-26 틱은 옛 고정 워치리스트 수집기 시절 것이다. 규칙은 전 기간 **지금
  라이브 플래그**를 적용한다.

## 2. 신호 생성 — 저장 틱·호가 리플레이

스크립트 `scripts/tick_replay_optimize.py` (읽기 전용 DB, 주문 경로 없음, 캐시 멱등).

- 틱 로드·감지기 투입은 `cli_pair_detect` 의 `_fetch_ticks`·`_feed` 를 **import 해서**
  쓴다(pair_sweep 과 같은 원칙 — 복사본 금지). 가드도 실제 `RiskGuard` 다.
- 호가: `quotes` 10호가를 `PairDetector.on_quote(bids=, asks=)` 로 넣는다(라이브
  `run_live` 와 같은 호출). 같은 초의 틱과 호가는 **틱 먼저, 그 초의 호가 나중**
  (저장 호가는 초당 마지막 스냅샷이라 먼저 넣으면 1초 미만 선견이 생긴다).
- 감지기 설정 = `pair_detect_daily.sh` 의 라이브 플래그를 `build_parser()`/
  `build_config()`/`build_guard()` 로 그대로 파싱한 것. 방아쇠(3호가 근접+서지 AND·
  VI 근접), 대량체결 2건, premove 0.2%, cosurge 0, manju 서열, 매수벽·매도폭탄·정체·
  1호가 하락 대장이탈 전부 라이브 그대로.
- **감지기 등록 모델(R-stored)**: 그날 틱이 저장된 **모든 종목**을 동적 유니버스로
  등록하고, 각 종목은 **첫 저장 틱 시각**부터 감지기에 보인다(구독 시점 근사).
  섹터(`stocks.sector`), 실전 테마(`theme_members` 중 `snapshot_date < 그날` 최신),
  전일종가(`daily_bars` 중 `date < 그날` 최신 종가)를 라이브 `_breaking_meta` 와 같은
  방식으로 주입한다.
  - **라이브와 다른 점(미리 밝힘)**: 라이브는 수집채움 종목을 감지기에 등록하지
    않고, 대장스캔은 09:00~10:00 에만 새 대장을 붙인다. 등록 이력(시각·코드)은 로그에
    남지 않는다. R-stored 는 **라이브 등록 집합의 상위집합**이다 — 라이브보다 신호가
    많을 수 있다.
- 가드: 킬스위치(연속손절·일일손실·반납·낙폭 축소)·동시보유 상한 **끔**. 포지션 수명이
  서로 독립이어야 게이트를 사후에 적용해도 결과가 같다(§3). 실전 1주 매매와 달리
  모든 통과 신호를 따로 잰다.
- 불타기(`--pyramid-arm`)는 실행기 전용이라 가드 회계에 없다 — 반영 안 함.

### 2-1. 패리티 체크 — 그리드 전에

2026-09-14 를 라이브 config 로 리플레이해 로그의 후보 신호 3건과 대조한다:

| 시각 | 대장→후속 | 로그 사유 |
|---|---|---|
| 09:09:00 | 411080→140430 | depth_short (진입 2,975) |
| 09:41:16 | 012210→053260 | roundtrip_bp 40.3bp (진입 8,160) |
| 12:05:27 | 069540→441270 | roundtrip_bp 32.8bp (진입 9,140) |

- **일치** 기준: 같은 대장→후속, 시각 ±5초, 같은 배제 사유, 진입가 동일, rt_bp ±5bp.
- 등록 모델 두 개로 잰다: R-stored(본 연구 모델)와 R-log(로그에서 복원한 감지기
  편입 종목만 — 장중 구독추가 줄 중 `[대장스캔]`·`[돌발재료]` 에 귀속되는 코드·선점
  코드 + 장전 유니버스 재구성). R-log 는 09-14 하루만 가능하다(옛 로그엔 날짜·코드가
  없다).
- 보고: 3건 중 몇 건 재현, **로그에 없는 추가 후보 수**. 3건 전부 재현 못 하면
  "리플레이가 라이브를 재현하지 못한다"고 쓰고, 이 연구가 재는 것은 "라이브 규칙을
  저장 틱 유니버스에 적용한 반사실"이지 라이브 자체가 아님을 결과에 명시한다.
  **패리티가 나빠도 사전등록된 측정은 그대로 진행한다**(멈추면 그것도 결과 선택이다).

## 3. 그리드 — 48셀

```
max_roundtrip_bp   30(라이브) | 60 | off
depth_short 배제   on(라이브) | off      (off = 10호가로 1천만원 못 채워도 통과)
min_sl_ticks       3(라이브) | 0
진입 컷오프         10:00(라이브) | 없음
국면 정지           라이브 5조 규칙(전일 코스닥 거래대금 < 5조면 신규 진입 0) | off
프로그램 수급 게이트  리플레이에선 off 고정 — 아래
체결 가정           through(주) · touch(병기)
```

3×2×2×2×2 = **48**.

**프로그램 수급 게이트는 축에서 뺀다.** ka90005 원자료는 저장되지 않는다. 로그의
전이 통지(`[프로그램수급] HHMMSS … 차단/회복`)는 날짜 태그가 09-10 이후에만 있어
16일 중 3일만 복원된다. 리플레이는 이 게이트 없이 잰다 — 라이브보다 진입이 많을
수 있다(09-14 라이브는 09:00~09:18, 09:20~ 차단이었다).

**구현상 사실(측정 전 코드 확인):** 감지기는 쿨다운(`_last_alert`)을 필터 **앞에서**
소비하므로 필터 설정이 후보 신호열 자체를 바꾸지 않는다. 그래서 감지기는 날마다
필터를 전부 끈 채 한 번 돌리고, 각 후보에 그 순간의 10호가 왕복충격(bp, 1천만원)과
손절폭 틱수를 기록한 뒤 필터·컷오프·국면 게이트를 **사후 적용**한다. 가드 포지션이
서로 독립(§2)이라 이 방식은 셀마다 따로 돌린 것과 같다. 틱 수준 동치 여부는
패리티 표에서 확인한다.

모든 셀을 `research/logs/75-tick-replay/TRIALS.jsonl` 에
`krx_quant_core.stats.trials.record_trial` 로 기록한다.

## 4. 진입·청산

- 진입: 감지기 진입 지정가 = 현재가 + 2호가(`--entry-ticks-up 2`). 체결은 through
  (체결가 < 지정가) 주, touch(≤) 병기. **체결가 = 지정가**로 계상한다.
  청산시각(180초)까지 미체결이면 거래 아님.
- 청산: 라이브 가드 규칙 그대로 — 익절 없음 · 약손절 −0.5%(대장 굳힘 중 잠금) ·
  재난선 −2% · 본절탈출(1호가 30초) · 트레일 +3% 무장/1.5% · 대장이탈(정체 15초·
  1호가 하락·벽 30% 감소 3초·매도폭탄 1억) · 시간청산 180초. 청산 **시각**은 가드가
  정한다.

## 5. 비용

- **PRIMARY(판정용) — 실전 1주 비용**: 청산가 = 가드 청산 시각의 **직전 매수1호가**
  (그 시각 이하 마지막 `quotes.bid1` 또는 틱 `best_bid` 중 늦은 것; 없으면 체결가).
  순수익 = 청산매수호가/진입지정가 − 1 − `round_trip_cost(그날, 시장)`
  (krx_quant_core: 수수료 0.015%×2 + 그날 매도세. 2026 년 KOSPI·KOSDAQ 모두 0.20%
  → 23bp).
- **SECONDARY(규모 관점)**: 가드 청산 체결가 기준 세전 − 64bp − 그 신호의 1천만원
  왕복충격 실측 bp. 충격을 못 잰 건(호가 없음·depth_short)은 이 열에서 빠진다.

## 6. IS 선택 규칙 — 고정

- 목적함수: **IS 일평균 순수익(PRIMARY, through)** = 거래가 1건 이상인 IS 날들의
  "그날 평균 순수익"의 평균.
- 자격: IS 체결 거래 **n ≥ 20**. 자격 셀이 없으면 선택 없음 → OOS 는 라이브만 계산,
  판정 "표본 부족 — 판정 불가".
- 동률(소수 6자리)이면 라이브에서 **덜 풀린** 셀(축 변경 수가 적은 것).
- 선택 셀이 라이브 config 와 같으면 OOS 는 라이브 한 번이다.

## 7. 채택 게이트 — AND, OOS, PRIMARY·through

1. OOS 순수익 **평균 > 0 그리고 중앙값 > 0**
2. **날짜 클러스터 부트스트랩**(OOS 날짜를 복원추출, 10,000회, seed 75) 평균의
   95% CI 하한 > 0
3. **상위 1% 제거 후 평균 > 0** (제거 건수 = ceil(0.01·n), 최소 1건). 승률 규칙은
   쓰지 않는다 — 익절 없는 우측꼬리 설계라 승률 < 50% 가 설계상 정상이기 때문이고,
   대신 꼬리 한두 건 의존을 막는 규칙을 고른다.
4. **주별 폴드**: 16일 전체를 달력 주 4개(08-24주·08-31주·09-07주·09-14주)로 나눠
   주별 평균 순수익이 음수인 주 ≤ 1 (거래 0건 주는 세지 않음)
5. **Deflated Sharpe 확률 > 0.95** — `deflated_sharpe_from_sample(OOS 건당 순수익,
   N)`, **N = 48 + 30 = 78**. 30 은 54번 백로그가 스스로 센 누적 시험 수
   ("06번부터 30건에 근접" — 사전등록 문서 24건 + 반사실·스윕류). 참고로 manju
   최적화 240셀까지 넣은 N = 318 도 병기하되 판정은 78 로 한다.
6. **무작위 대조군을 이긴다**: 선택 셀의 각 OOS 후보 시각에 그 순간 구독 중이던
   (그 시각 ±60초 안에 틱이 있는) **다른 종목 하나**를 무작위(seed 고정)로 골라,
   같은 대장·같은 청산 규칙·같은 비용으로 잰다. 날짜 짝지은 부트스트랩
   (`paired_date_bootstrap`, 10,000회)에서 p = P(차이 ≤ 0) < 0.05.
7. **OOS 거래 ≥ 30**. 미달이면 판정은 "**표본 부족 — 판정 불가**"이고 채택이 아니다.

## 8. 채택·기각의 의미

- **채택 = 즉시 라이브 변경이 아니다.** 선택 셀의 플래그 변경안을 만들고, 1주일
  그림자 비교(라이브 config 와 나란히 기록)를 거친 뒤 사용자 결정.
- **기각 = 기록하고 멈춘다.** 축을 바꾸거나 기간을 늘려 재튜닝하지 않는다. 새 데이터
  종류(등록 이력 로그·프로그램 수급 저장 등)가 생기면 그건 **다른 사전등록**이다.
- 선택 셀이 라이브와 같으면 "변경할 근거 없음"이고, 라이브 자체의 OOS 도 게이트로
  같이 보고한다.

## 9. 맥락 보고(선택·판정에 안 씀)

- 09-14 후보 3건이 필터 없이 들어갔다면 실현됐을 결과(PRIMARY·through).
- 셀별 **일자별 거래 수**(왜 적은가: 후보 → 필터 → 컷오프 → 국면 → 체결 단계별 감소).
- 비용 민감도: PRIMARY / SECONDARY / 세전.

## 10. 미리 밝히는 한계

- **등록 집합이 라이브의 상위집합**(§2). 대장스캔 시간창·수집채움 비등록을 재현 못 한다.
- **프로그램 수급 게이트 없음**(§3).
- **호가는 초당 마지막 스냅샷** — 초 안의 호가 변동, 대기열 위치를 모른다.
- **청산 매수호가는 1주 기준** — 1호가 잔량이 0에 가까운 순간은 고려 안 함.
- 16일 전부 국면이 침체·극침체·중간 위주(활황은 09-11 하루 — 전일 09-10 11.4조) — 활황 일반화 불가.
- 체결가 = 지정가(현재가+2호가) 가정은 매도1호가 체결보다 비관적이다.
