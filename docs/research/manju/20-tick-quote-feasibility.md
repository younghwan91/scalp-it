> 2026-08-23. 읽기 전용 조사(에이전트)가 키움 WebSocket 을 실호출로 확인. **틱 히스토리 소급 불가 → 지금부터 실시간만.** 데몬 착수는 사용자 승인 대기.

**실제 토큰 발급·REST 3종·WebSocket LOGIN/REG/한도까지 실측**했다. "확인" = 오늘 실호출로 검증,
"표준/미확인" = 문서·통설이며 장중 재확인 필요.

## 0. 한 줄 결론

**가장 빠른 경로 = 키움 WebSocket 실시간 데몬.** 이미 있는 키움 인증으로 오늘 실측에서
WebSocket `LOGIN`·`REG`(체결 0B + 호가 0D)가 모두 `return_code=0` 으로 붙었고,
실시간 체결이 **체결강도·매수/매도 방향**을 준다(REST 프록시 `ka10003` 로 필드 실측).
막힌 것: **틱 히스토리 소급 수집은 사실상 불가**(만쥬 신호인 체결강도·방향이 든 `ka10003` 은
30행/페이지·얕은 깊이라 하루 전체 백필이 수천 콜, `ka10079` 틱차트는 깊이는 되나 체결강도·방향이 없음).
→ **지금부터 실시간으로 쌓는 수밖에 없고, 그건 오늘 바로 가능하다.**

## 1. 키움 실시간(WebSocket) — 확인됨

- **엔드포인트(확인):** `wss://api.kiwoom.com:10000/api/dostk/websocket` (모의 `wss://mockapi.kiwoom.com:10000`).
- **프로토콜(실측):**
  1. `{"trnm":"LOGIN","token":"<REST 토큰 그대로>"}` → 응답 `{"trnm":"LOGIN","return_code":0,"sor_yn":"Y"}` ✔
  2. `{"trnm":"REG","grp_no":"1","refresh":"1","data":[{"item":["005930","000660"],"type":["0B","0D"]}]}`
     → 응답 `{"trnm":"REG","return_code":0}` ✔ (주말이라 REAL 푸시는 없음 — 정상)
  3. 장중엔 `{"trnm":"REAL","data":[{"type":"0B","item":"005930","values":{"<FID>":"..."}}]}` 가 push.
  - 토큰은 **기존 REST 토큰과 동일**. WebSocket 전용 인증이 따로 없다.
- **19종 실시간 type 중 우리에게 필요한 것:**
  | type | 내용 | 만쥬 신호 |
  |---|---|---|
  | `0B` | 주식체결(틱) | **체결시각·체결가·체결량(부호=매수/매도)·체결강도·누적거래량·최우선호가** ← 핵심 |
  | `0D` | 주식호가잔량 | **10호가 잔량·총매수/총매도잔량** ← 상따 잔량소진용 |
  | `0C` | 주식우선호가 | 최우선호가만 (경량) |
  | `1h` | VI 발동/해제 | 변동성완화장치 (스캘핑 진입 트리거) |
  | `0E` | 시간외호가 | 시간외단일가 |
- **동시 구독 한도(실측):** 한 커넥션에서 REG 를 누적하다가 **약 100건(종목×type)** 에서
  `return_code=105110 "해당 TRNM으로 허용된 요청 건수를 초과하였습니다"`. (20종목×5그룹=100 OK, 6번째서 거부.)
  - 즉 커넥션당 등록 ≈ **100건**. 한 종목에 체결+호가 둘 다면 2건 → **커넥션당 ~50종목(0B+0D)** 또는 ~100종목(0B만).
  - **미확인:** 계정당 커넥션 여러 개 허용 여부(여러 소켓으로 확장 가능한지), type이 종목당 곱으로 세는지 정확 회계.
- **0B/0D 필드(FID) — 표준값, 장중 REAL 프레임에서 최종 확인 필요:**
  - 0B: `20`체결시각 `10`현재가 `11`전일대비 `12`등락율 `15`체결량(±=매수/매도) `13`누적거래량 `228`체결강도 `27`최우선매도호가 `28`최우선매수호가
  - 0D: `21`호가시각 `41~50`매도호가1~10 `51~60`매수호가1~10 `61~70`매도잔량1~10 `71~80`매수잔량1~10 `121`총매도잔량 `125`총매수잔량

## 2. 키움 REST 당일 조회 — 실측 (백필용으로는 부족)

| TR | 경로 | 실측 결과 | 만쥬 신호 |
|---|---|---|---|
| `ka10003` 체결정보 | `/api/dostk/stkinfo` | **30행/페이지**, 필드 `tm,cur_prc,cntr_trde_qty(±=매수/매도),cntr_str(체결강도),acc_trde_qty,pri_sel/buy_bid_unit` | 체결강도·방향 **있음**. 그러나 60페이지(1,800행)가 겨우 40분치 → 하루 전체 백필은 수천 콜, 비현실적 |
| `ka10079` 주식틱차트 | `/api/dostk/chart` | 900행/페이지, `cont-yn=Y` 로 과거까지 페이지네이션(30p=27,000행≈45분), `cntr_tm,cur_prc,trde_qty,OHLC` | 가격·거래량은 소급되나 **체결강도·방향 없음** → 만쥬 신호 아님 |
| `ka10004` 주식호가 | `/api/dostk/mrkcond` | **스냅샷 1건**: 10호가 매도/매수 잔량 + `tot_sel_req/tot_buy_req` + 시간외 | 호가 잔량 **있음(스냅샷)**. 소급 불가, 폴링만 가능 |

- **핵심:** REST로 호가 스냅샷(`ka10004`)·체결(`ka10003`)을 폴링해 쌓는 것도 가능은 하지만,
  틱은 초당 수십 건이라 `ka10003`(30행/콜, ~5req/s rate) 폴링으로는 활황 종목의 체결을 놓친다.
  **체결 유입의 순간을 온전히 잡으려면 WebSocket 0B 가 정도.** 호가는 REST 폴링(1초 간격)로도 대체 가능.

## 3. 저장 규모 · 테이블 설계

- 활황 이벤트 종목 하루 체결 수: 대략 2만~10만 틱(급등 소형주는 더). 0D(호가)는 체결보다 잦아 종목당 수십만 업데이트/일.
- **권장 정책:** 체결(0B)은 전량 저장, 호가(0D)는 **① 체결 행에 최우선/총잔량을 조인**하거나 **② 1초 스냅샷**으로 다운샘플(전량 저장은 5~10배 비쌈).
- **추정(종목 100개, 0B 전량 + 0D 1초 스냅샷):** 미압축 ~1 GB/일 → TimescaleDB 압축(~10x) **~100 MB/일**.
  3~6개월(≈120거래일) ≈ **15~40 GB 압축**. 분봉과 같은 `KR_QUANT_DB` 에 충분히 수용.
- **테이블(분봉 `minute_bars` 와 같은 DB, 신규 하이퍼테이블 2개):**
  ```sql
  -- 틱: 초당 다건 → (code, ts) 만으로는 PK 불가. seq 또는 bigserial 필요
  CREATE TABLE ticks (
    code text, ts timestamp, seq int,           -- seq: 같은 초 내 순번(수신 순)
    price int, signed_qty int,                  -- 부호=매수(+)/매도(-)
    acc_qty bigint, strength double precision,  -- 체결강도
    ask1 int, bid1 int,
    PRIMARY KEY (code, ts, seq));
  CREATE TABLE quotes (                          -- 1초 스냅샷 또는 체결조인
    code text, ts timestamp,
    ask_px int[10], ask_qty int[10],
    bid_px int[10], bid_qty int[10],
    tot_ask bigint, tot_bid bigint,
    PRIMARY KEY (code, ts));
  -- SELECT create_hypertable('ticks','ts'); ALTER TABLE ticks SET (timescaledb.compress...);
  ```
  기존 `store.py` 패턴(postgres/sqlite 양립, upsert)을 그대로 복제하면 된다.

## 4. 대안 소스 (키움이 정도라 백업용)

- **한국투자증권(KIS) REST+WebSocket:** 실시간 체결 `H0STCNT0`·호가 `H0STASP0`, 무료. 통상 세션당 ~40종목. 검증된 백업.
- **LS증권(구 이베스트) xingAPI/REST:** 실시간 체결·호가 제공, Windows/REST 혼용.
- **대신 크레온(CREON):** COM/OCX, 틱·호가 풍부하나 **Windows 전용**·상시 데스크톱 필요(운영 부담 큼).
- **KRX 정보데이터시스템 데이터상품:** 과거 체결/호가를 **유료 판매**(라이선스·고가, 대개 T+1). "히스토리 못 산다"는 전제의 예외이나 비싸고 실시간 엣지가 아님. 참고만.
- 결론: **이미 키움 실시간이 붙었으니 갈아탈 이유 없음.** KIS를 백업으로만.

## 5. 최소 착수 형태 (오늘부터 쌓으려면)

1. **WebSocket 데몬**(asyncio ~150줄 또는 사용자 자체 래퍼 `younghwan91/kiwoom-client` 재사용):
   connect→LOGIN(기존 토큰)→REG(0B+0D)→listen, 끊기면 재연결+재REG, 배치 insert.
2. **구독 종목 = 전일 이벤트 후보 ~50~100개**: 기존 스캐너(`scripts/*_events.py`, `top_universe`)를
   장전(08:50)에 돌려 후보 리스트 생성 → REG. 0B+0D면 커넥션당 ~50종목이라 **커넥션 1~2개**.
3. **장 시간 09:00~15:30**(선택 15:30~16:00 시간외 0E). cron 08:50 기동 / 15:40 종료(또는 systemd).
4. **저장:** `KR_QUANT_DB` 에 `ticks`/`quotes` 하이퍼테이블 신설(위 3장).
5. **첫 검증까지:** 후보 수십 개 중 실제로 체결강도 급증하는 에피소드는 하루 수 건 →
   **2~4주면 수십 에피소드**로 첫 sanity check("체결강도 급증 → 다음 N분 수익") 가능,
   정식 판정은 STATUS대로 **3~6개월** 축적 후.

## 6. 막힌 것 / 장중 확인 필요

- 틱 **히스토리 소급 불가**(체결강도·방향 든 소급 소스 없음) → 지금부터 실시간만.
- 0B/0D **REAL 프레임 실제 FID 필드명**은 장중 1회 확인(표준 FID로 코딩 후 대조).
- **0B·0D가 종목당 각각 1건으로 세는지**(→ 커넥션당 ~50종목) vs 종목 단위(→ ~100종목), **다중 커넥션 허용 여부** — 장중 실측.
- **토큰 동시성:** 기존 REST 수집기(분봉·테마)와 새 WS 데몬이 같은 appkey 토큰을 동시에 오래 쓸 때 충돌 여부 — 장중 확인(오늘 반복 발급은 문제없었음).
